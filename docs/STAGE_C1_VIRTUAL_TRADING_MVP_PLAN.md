## 2. Proposed minimal architecture

One local **virtual** portfolio, INR, cash equities only, no borrowing, leverage, shorting, derivatives, broker access or market-data calls. Start it with one idempotent deposit of **1,000,000 paise** (₹10,000). Use a separately migrated, git-ignored SQLite file, for example `data/virtual_mvp.db`, and a dedicated virtual session dependency. Reject startup if its resolved path is the configured production DB or a canonical/pilot/provisional DB. Do not copy production rows. The existing ledger tables, `LedgerService`, valuation service and report service remain the accounting engine. Use `Instrument`/`DailyPrice` in that **virtual database only** for a small, versioned, synthetic EQ quote fixture with explicit provenance and a fixture hash; do not route it through the NSE ZIP importer or claim NSE provenance. Prices, dates, source and the **SYNTHETIC DEMO — NOT MARKET DATA** label must appear on every order preview and valuation. No provisional FYERS observation may be copied or queried.

An authenticated `VirtualOrderService` should select the latest completed synthetic quote on or before the virtual decision time, validate quote freshness and symbol allowlist, calculate an adverse illustrative fill price and itemized charges, build a fresh portfolio snapshot, invoke the **existing** `RiskValidator`, apply the extra fixed paise caps within that same deterministic gate, then call the existing ledger buy/sell method only on approval. The service must not trust browser-supplied prices, fees, approval flags or account IDs. Order preview is informative; submission recomputes all facts under a write transaction and can reject if state changed. A stop entered for a buy is a **risk-planning input**, not a guaranteed fill or automatic protective order. Manual sell and buy orders fill against the selected synthetic quote only; this is an exercise, not an execution-quality simulator.

The current manual ledger routes are intentionally risk-free historical recording (`backend/app/api/routes/portfolio.py:84-137`). They **must be disabled for the virtual database** while retained unchanged for the real historical ledger. Otherwise a user could bypass the virtual risk gate with `/portfolio/buys`. Route-level virtual-mode separation must be tested. The virtual API must remain behind the existing bearer-token dependency (`backend/app/api/router.py:11-18`) and loopback-only frontend proxy.

For durable order audit and idempotency, add **one narrow migration** for `virtual_order_attempts` in the virtual schema only: unique idempotency key plus request hash, UTC attempted time, symbol/side/quantity/stop, synthetic quote ID/date/hash, reference and fill prices, slippage, charge breakdown/profile version, snapshot/risk-limit version, all rejection codes, status, and nullable linked `ledger_transaction_id`. Do not make a second lot/cash table. Reusing an idempotency key with a different payload must fail; replay of a completed key returns the original result. Rejected attempts are recorded without a ledger trade. Because `LedgerService` currently commits internally (`backend/app/modules/portfolio/ledger_service.py:164,292`), introduce the smallest transaction-control seam so the virtual service can commit approved attempt, fill, lot changes and vault changes **atomically**, while preserving existing historical API behavior. Serialize virtual submissions around snapshot/validate/fill (SQLite write transaction), so concurrent orders cannot both spend the same cash.

## 3. Risk and accounting invariants

- Configure fixed virtual caps in integer paise: planned loss per new buy **5,000**, daily net realized-loss threshold **10,000**, and post-buy single-symbol open-cost exposure **200,000**. Enforce them together with the existing percent limits; whichever is stricter applies. With initial ₹10,000, the existing 10% max-order rule permits at most about ₹1,000 per initial buy even though stock exposure allows ₹2,000 across buys. Percent limits change with risk capital; fixed paise caps do not.
- Planned loss = `(adverse synthetic fill price - stop price) × whole shares + estimated buy and exit charges` (and a stated adverse exit-slippage assumption). Reject if above ₹50 or stop is absent/invalid. This is a **budgeted scenario**, not a guaranteed maximum realized loss: gaps, illiquidity, stops not executing and costs can make actual loss larger. Display that warning. If the estimate cannot be calculated, fail closed.
- Daily realized loss uses the existing Asia/Kolkata date boundary and realized FIFO events, net of fees; at or beyond ₹100, further **buys** are blocked. Sells remain permitted up to held quantity, including stop-outs after the threshold. Persist the fill timestamp in UTC. Test midnight IST and loss/gain combinations explicitly.
- Buy: check deployable cash including all charges, no negative cash, no spending reserved vault, stock cap and existing concentration/order caps. Sell: no shorting; net proceeds, FIFO lot reductions, realized P&L and positive Profit Vault credit remain one atomic transaction. Losses never debit the vault. Persist every accepted fill in the existing append-only ledger; no edit/delete endpoint.
- Valuation uses only the dated synthetic close. Unpriced or stale positions show unavailable and separate cost, never zero market value. Display realized and unrealized P&L separately. No implied profitability or advice.

## 4. Minimal UI and API work

| Surface | Proposed contract |
| --- | --- |
| `GET /api/v1/virtual/account` | Cash, deployable cash, vault, holdings, cost basis, realized P&L, dated synthetic valuation, and explicit synthetic/virtual identity. Derive using existing services. |
| `GET /api/v1/virtual/quotes` | Only allowed fixture symbols with quote price/date/source/fixture hash and stale or unavailable state. No FYERS or canonical price path. |
| `POST /api/v1/virtual/orders/preview` | Side, symbol, whole quantity, buy stop; return revalidated quote, estimated fill/slippage/charges, cash impact, planned risk and all gate reasons. No write. |
| `POST /api/v1/virtual/orders` | Same payload plus required idempotency key; reprice and revalidate under a transaction, then append one accepted fill or a rejected attempt. No broker order. |
| `GET /api/v1/virtual/orders` | Filled and rejected attempt history with timestamps, quote reference, fees, risk reasons and ledger transaction link. Existing CSV/FIFO report code can be reused for virtual ledger data. |

Frontend: add one `VirtualTradingPanel` with a persistent **synthetic demo** banner, ₹10,000 seed/cash card, dated quotes, buy/sell ticket, required buy stop, preview/confirm step, full itemized costs and cash impact, all risk rejection reasons, uncertain-network retry with the same persisted idempotency key, holdings and realized/unrealized P&L, vault balance, and attempt history. Reuse `frontend/src/api/client.ts`, `frontend/src/lib/ledger.ts` paise formatting/conversion, and the pending-key pattern from `LedgerEntryPanel`. Keep historical-entry forms visibly separate; never present them as virtual order tickets. The browser receives no auth token or raw credential.

## 5. Ordered implementation tasks

1. Add a guarded virtual configuration/database session and a private, idempotent bootstrap that seeds **only** the isolated virtual DB with ₹10,000 and a few fictional EQ symbols/dated deterministic synthetic prices. Validate fixture schema, provenance, hashes and quote dates. No schema change for cash/lots/prices.
2. Add the narrow virtual-attempt migration and transaction seam, then implement snapshot → risk → atomic ledger fill/audit in one service. Add fixed paise cap options to the existing pure risk validator, defaulting to absent for current users. Block historical POSTs in virtual mode. Keep sell exits available after loss limits.
3. Add only the virtual routes/schemas and typed client. Build the single panel by reusing display and form utilities. Keep the quote and every value labeled synthetic and dated.
4. Test, then demonstrate locally against the isolated virtual DB. Preserve production DB, `pilot.db`, `provisional.db`, all 95 provisional candles and existing market-data pipeline unchanged. No new package is expected; FastAPI, SQLAlchemy, Pydantic, React and the current test tools suffice.

## 6. Acceptance tests

Backend (temporary SQLite databases and synthetic fixtures only): one-time ₹10,000 bootstrap and restart; real/virtual DB path collision refusal; virtual endpoint authentication and historical-POST bypass refusal; preview has no writes; quote date/staleness/future/cross-source rejection; integer-paise fee/slippage arithmetic; planned-risk ₹50 boundary including costs; daily net loss ₹100 at IST midnight; ₹2,000 stock exposure at and over boundary; existing percent limits still apply; overspend, short sell, stale preview and missing stop reject; rejected order writes no ledger transaction; approved buy/sell has FIFO cost/P&L/vault reconciliation; duplicate key replay, changed-payload conflict, concurrent spend, and mid-fill rollback leave a consistent audit and ledger. Verify no access to provisional or production DB paths and no broker/network call.

Frontend: synthetic banner and price date always visible; exact paise totals and warning on stop limitations; buy/sell preview and confirmation; all risk reasons; no hidden historical-POST path; double-click and reload retry preserve key; priced/unpriced/error states; trade-history and Profit Vault displays; no fabricated return claims. Run current backend/frontend suites, Ruff, mypy, frontend lint/build, and virtual flow end-to-end before calling the MVP complete.

## 7. Local demonstration after implementation

1. Back up the existing real DB and leave it offline. Create a fresh **separate** virtual SQLite file, apply existing migrations plus the virtual-attempt migration there, and run the proposed idempotent synthetic seed. Verify its absolute path differs from every real, pilot and provisional database path. Do not seed `data/investment_agent.db`.
2. Start the backend and Vite frontend on `127.0.0.1` using the virtual-mode configuration and existing server-side auth proxy. Open the virtual panel; verify opening cash ₹10,000, no holdings and an unmistakable synthetic label/date.
3. Preview a small buy of a fictional symbol with a valid stop. Confirm and verify the accepted fill, reduced cash, FIFO cost, dated synthetic market value and itemized illustrative costs. Preview an over-budget buy and a missing-stop buy; verify all rejection reasons and no ledger change.
4. Sell part of the holding; verify remaining FIFO quantity/cost, net proceeds, realized P&L, vault credit only when positive, and attempt/ledger history. Refresh and retry the same key to verify one fill. Check that the historical manual `/portfolio/buys` route is refused in virtual mode. Stop both servers; keep the virtual DB private and git-ignored.

## 8. Effort, dependencies and limits

Estimate **2–4 focused coding days** plus a local demonstration, assuming the existing migration/session patterns can be reused and no unexpected transaction-boundary issue appears. Sequence: isolated DB/fixture (0.5 day), atomic order/risk/audit and tests (1–2 days), UI/API and tests (0.5–1 day), end-to-end verification (0.5 day). No new third-party dependency is expected. The work depends on an explicit synthetic fixture and an illustrative, versioned cost profile; broker-exact costs, fill quality and stop execution cannot be asserted. No ML signals, actual exchange prices, real broker orders or automatic stops are part of this MVP.
